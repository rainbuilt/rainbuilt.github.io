소유권과 입력 검증, 트랜잭션 처리를 구현했습니다.
데이터 수집외부 게시물에서 작품과 촬영지 정보를 수집하고,

프론트엔드지도와 전역 일정 편집기를 구현하고,

협업과 배포FastAPI Mock 서버로 화면 개발을 진행할 수 있게 하고,
GitHub Actions로 빌드와 배포를 자동화했습니다.

편집한 일정이 그대로 저장되도록

Java 21 / Spring Boot 3 / MyBatis / MySQL

일정 저장의 단위

사용자는 한 번의 편집에서 장소를 추가하고, 기존 일정을 수정하거나 삭제할 수 있습니다. 각 변경을 따로 저장하면 일부만 반영될 수 있다고 판단했습니다. 화면과 DB의 상태가 어긋나지 않도록 전체 편집 결과를 한 요청으로 받아 검증한 뒤 함께 저장했습니다.

저장 전에 확인한 조건

검증 대상처리 규칙
계획 소유권인증 사용자와 계획 소유자가 일치하는지 확인합니다.
날짜와 시간날짜와 시간 형식을 검증하고 여행 기간 밖의 일정을 거부합니다.
세부 일정 ID중복 ID와 해당 계획에 속하지 않은 ID를 거부합니다.
일정의 장소촬영지와 일반 장소 중 하나만 참조하고 존재 여부를 확인합니다.

삭제부터 추가까지 하나의 트랜잭션으로

전체 입력의 검증이 끝나면 요청에서 빠진 기존 항목을 삭제하고, ID가 있는 항목은 수정하며, ID가 없는 항목은 추가했습니다. 이 과정을 @Transactional로 묶어 처리 중 오류가 나면 변경이 함께 롤백되도록 했습니다.

응답과 DB 결과를 함께 검증

Testcontainers 기반 MySQL 환경에서 통합 테스트 33개를 구성했습니다. 정상 처리, 권한 오류, 입력 오류를 검증하고, 일정 동기화에서는 응답과 DB를 함께 확인해 삭제, 수정, 추가가 의도대로 반영되는지 점검했습니다.

데이터 수집 배치

여섯 단계로 나눈 수집 과정

외부 게시물을 활용하려면 작품명을 맞추고, 주소를 좌표로 바꾸고, 이미지를 저장해야 했습니다. 실패한 지점을 확인하고 다시 처리할 수 있도록 Spring Batch의 단계별 작업으로 나누었습니다.

  1. 01게시물 탐색수집 대상 등록
  2. 02본문 파싱작품과 장소 추출
  3. 03작품 매칭TMDB 정보 연결
  4. 04촬영지 저장주소 검증과 좌표화
  5. 05이미지 저장WebP 변환 후 S3 저장
  6. 06결과 집계처리 상태 확인

모호한 후보를 처리하는 기준

제목만으로 작품을 확정하지 않도록 대체 제목, 국가, 언어, 연도도 점수에 반영했습니다. 기준 점수와 상위 두 후보의 점수 차를 함께 확인하고, 조건을 만족하지 못한 작품이나 주소가 모호한 촬영지는 검수할 수 있도록 중간 상태로 남겼습니다.

실패한 실행을 이어서 처리하기

게시물, 촬영지, 이미지의 처리 상태를 staging 테이블에 저장했습니다. 실행이 실패하면 같은 ingestKey로 완료된 단계 이후부터 이어가도록 구성했습니다. 오류 코드와 메시지도 남겨 재처리 대상을 확인할 수 있게 했습니다.

실패한 실행의 재시작은 같은 ingestKey, 완료 후 새 수집은 새로운 ingestKey

외부 호출과 중복 저장 관리

외부 API에는 호출 속도 제한과 재시도를 적용하고, 재시도 가능한 오류를 구분했습니다. 이미지는 WebP로 변환한 뒤 SHA-256 기반의 S3 키를 사용해 같은 콘텐츠가 중복 업로드되는 것을 줄였습니다.

매칭과 재실행 기준 검증

12개 클래스에 배치 테스트 28개를 작성했습니다. 모호한 작품 후보의 거부, 동일 이미지의 S3 키 일치, 입력 순서에 따른 수집 키의 안정성을 확인했습니다. 실패 상태 점검 SQL과 재시작 절차도 문서로 남겼습니다.
